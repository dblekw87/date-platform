# KR Search Experience Planner

## 문서 목적

이 문서는 KR Prototype B의 검색 화면을 구현하기 전 경험 구조를 정의한다.

이번 문서는 React 구현, SCSS 작성, Route 수정, Wireframe 구현, 공통 Component 추가, Mock 데이터 구현, Commit을 다루지 않는다. 목적은 사용자가 종목, 기업, 테마, 공식 정보, 시장 변화, 기존 Analysis, 관심 종목을 빠르게 찾고 적절한 다음 Research 행동으로 이어지는 Search 경험을 설계하는 것이다.

Prototype A의 Discovery 화면을 번역하거나 복사하지 않는다. KR Search는 한국 투자자가 익숙한 종목명·종목 코드 검색을 출발점으로 삼되, DATE의 공식 Evidence, Analysis, Watchlist, Changes 흐름으로 자연스럽게 이어지는 발견 진입점이다.

## 1. Search Product Goal

### Search는 왜 존재하는가

Search는 사용자가 이미 찾고 싶은 대상이 있을 때 가장 빠르게 해당 대상과 다음 화면으로 이동하기 위해 존재한다.

Search는 종목명 검색창만이 아니다. Search는 사용자가 입력한 단어를 종목, 기업, 테마, ETF, 시장, 공식 Evidence, 기존 Analysis, Watchlist 목록, Changes 항목 중 어떤 대상으로 볼 수 있는지 해석하고, 사용자가 확인해야 할 공식 정보와 다음 행동을 함께 연결한다.

Search의 핵심 목표는 검색 결과를 많이 보여주는 것이 아니다. 사용자가 찾는 대상, 확인해야 할 공식 정보, 다음 Research 행동을 빠르게 연결하는 것이다.

### 사용자가 Search를 여는 대표 상황

- 종목명이나 종목 코드를 바로 알고 있다.
- 기업명은 알지만 상장 종목이나 시장을 모른다.
- 테마명을 검색해 관련 종목과 공식 정보를 보고 싶다.
- 공시 제목, 기관명, 발표명을 기억한다.
- 이전에 보던 Analysis를 다시 찾고 싶다.
- 관심 종목에 추가할 대상을 찾고 싶다.
- Home이나 Market에서 본 키워드를 더 좁혀 보고 싶다.
- Changes에서 본 변화의 관련 종목이나 Evidence를 다시 찾고 싶다.

### Search 이후 이어져야 하는 화면

Search 결과는 다음 화면으로 이어진다.

- 종목 결과 → Stock Detail
- 기업 결과 → 대표 종목 또는 기업 상세 후보
- 테마 결과 → Market 또는 Theme 상세 후보
- ETF 결과 → Stock Detail 또는 Market
- 시장 결과 → Market
- Evidence 결과 → Evidence Detail
- Analysis 결과 → Analysis Detail
- Watchlist 목록 결과 → Watchlist
- Changes 항목 결과 → Changes

Search는 상세 화면의 정보를 전부 반복하지 않는다. Search는 발견과 진입을 담당하고, 검증과 판단 구조 관리는 각 상세 화면이 담당한다.

## 2. Search 대상

### 검색 가능한 대상

필수 대상:

- 종목
- 기업
- 테마
- ETF
- 시장
- 공식 Evidence
- Analysis
- Watchlist 목록
- Changes 항목

### 권장 우선순위

검색 결과의 기본 우선순위는 다음과 같다.

1. 정확한 종목명 또는 종목 코드 일치
2. 정확한 기업명 또는 티커 일치
3. 사용자 관심 종목 또는 기존 Analysis와 연결된 대상
4. 새 공식 Evidence가 있는 대상
5. 공식 Evidence 자체
6. 테마와 ETF
7. 시장 기준점
8. Watchlist 목록
9. Changes 항목

이 순서는 고정 랭킹이 아니라 검색어 성격에 따라 조정된다. 예를 들어 “dart”나 공시 제목에 가까운 검색어는 Evidence를 상단에 둘 수 있고, “반도체”처럼 테마어가 명확하면 테마와 관련 종목을 함께 노출한다.

### 결과 유형 노출 원칙

한 검색 결과 화면에서 모든 유형을 동일한 위계로 섞지 않는다.

권장 구조:

```text
가장 정확한 결과
→ 종목
→ 기업
→ 테마 / ETF
→ 공식 Evidence
→ Analysis
→ Watchlist / Changes
```

이유:

- 사용자는 먼저 자신이 찾는 대상이 맞는지 확인해야 한다.
- 공식 Evidence와 Analysis는 다음 행동으로 이어지는 보조 맥락이다.
- 모든 결과를 같은 카드로 섞으면 종목, 기업, Evidence의 책임이 흐려진다.

## 3. Search 기본 단위

Search는 사용자가 입력한 검색어를 다음 단위로 해석한다.

- 종목명
- 종목 코드
- 기업명
- 영문 기업명
- 티커
- 테마명
- ETF명 또는 ETF 코드
- 시장명
- 공시 제목
- 공식 기관명
- Evidence 제목
- Analysis 제목
- Watchlist 목록명
- Changes 제목 또는 변화 유형

### 일치 방식

#### 정확 일치

우선순위가 가장 높다.

예:

- `005930` → 삼성전자 종목 결과
- `삼성전자` → 삼성전자 종목과 기업 결과
- `AAPL` → Apple 관련 종목 결과

#### 부분 일치

검색어가 종목명, 기업명, 테마명, Evidence 제목 일부와 맞는 경우 사용한다.

예:

- `삼성` → 삼성전자, 삼성SDI 후보
- `HBM` → SK하이닉스, HBM 테마, 관련 Evidence

#### 초성 검색

지원 후보로 둔다.

예:

- `ㅅㅅㅈㅈ` → 삼성전자

권장안:

- 한국 사용자의 기대가 높으므로 후속 구현에서 지원한다.

보류 이유:

- Low-Fi Planner에서는 UX 원칙만 정의하고 실제 검색 엔진 구현은 다루지 않는다.

#### 한글 / 영문 혼합

한글 기업명과 영문 티커를 모두 허용한다.

예:

- `엔비디아`, `NVIDIA`, `NVDA`
- `애플`, `Apple`, `AAPL`

#### 종목 코드 검색

종목 코드는 정확 일치를 우선한다. 숫자 6자리 입력은 국내 종목 코드 후보로 먼저 해석한다.

#### 공식 기관명 검색

기관명 검색은 Evidence 결과 우선순위를 높인다.

예:

- `DART`
- `거래소`
- `금융감독원`
- `기업 IR`

## 4. 검색 전 상태

검색 전 상태는 사용자가 최근 맥락으로 빠르게 돌아가게 하는 화면이다.

### 후보

- 최근 검색
- 최근 본 종목
- 최근 확인한 Evidence
- 관심 종목
- 이어서 볼 Analysis
- 오늘 많이 찾는 종목
- 주목받는 테마
- 새 공식 정보

### 권장 구조

검색 전 기본 노출:

1. 최근 본 항목
2. 이어서 볼 Analysis
3. 관심 종목
4. 최근 확인한 Evidence
5. 새 공식 정보

보조 노출:

- 주목받는 테마
- 오늘 많이 찾는 종목

### 주의

인기 검색어는 추천처럼 보이면 안 된다.

권장 문구:

- 많이 검색된 종목
- 오늘 자주 확인된 키워드
- 최근 많이 조회된 공식 정보

금지 문구:

- 추천 종목
- 지금 봐야 할 급등 종목
- 수익 기회
- AI 추천 검색어

검색 전 상태의 기본 목적은 사용자가 최근 맥락으로 돌아가는 것이다. 시장 전체 탐색은 Market이 담당한다.

## 5. 검색 중 상태

입력 중 자동완성은 사용자가 검색 결과 화면으로 이동하기 전에 빠르게 대상을 고르게 돕는다.

### 최소 구분

- 종목
- 기업
- 테마
- 공식 근거

### 종목 자동완성 결과

포함:

- 종목명
- 종목 코드
- 시장
- 현재 상태
- 관심 여부
- Analysis 존재 여부

표시 예:

```text
삼성전자 005930 · KOSPI
관심 종목 · Analysis 있음 · 새 공식 정보 2개
```

### 기업 자동완성 결과

포함:

- 기업명
- 대표 종목
- 산업
- 관련 시장

표시 예:

```text
Samsung Electronics
대표 종목 삼성전자 005930 · 반도체 · KOSPI
```

### 테마 자동완성 결과

포함:

- 테마명
- 관련 종목 수
- 새 공식 정보 여부

표시 예:

```text
반도체
관련 종목 12개 · 새 공식 정보 3개
```

### Evidence 자동완성 결과

포함:

- 제목
- 유형
- 공식 출처
- 공개 시각
- 확인 상태

표시 예:

```text
공급망 검토 대상 관련 전자공시
전자공시 · OpenDART · 오늘 09:30 · 공식 확인
```

### 자동완성 원칙

- 단순 가격과 등락률만으로 결과 순위를 정하지 않는다.
- 종목 결과와 Evidence 결과를 시각적으로 구분한다.
- 자동완성은 상세 내용을 다 보여주지 않고 진입에 필요한 정보만 압축한다.
- 키보드 탐색과 모바일 터치 선택 모두 가능해야 한다.

## 6. 검색 결과 우선순위

### 우선순위 기준

검색 결과 우선순위는 다음 기준을 조합한다.

- 정확한 이름 또는 코드 일치
- 사용자 관심 종목
- 기존 Analysis 연결
- 새 공식 Evidence 존재
- 최근 확인한 대상
- 현재 시장 관련성
- 공식성
- 검색어와의 의미적 관련성

### 낮은 우선순위 기준

다음은 핵심 우선순위 기준으로 사용하지 않는다.

- 단순 조회수
- 단순 급등률
- 거래량만 높은 종목
- 인기 검색어
- 광고성 노출

### 권장 정렬

```text
정확 일치
→ 내 문맥과 연결된 대상
→ 공식 정보가 있는 대상
→ 최근 확인한 대상
→ 의미적으로 관련된 대상
```

이 정렬은 투자 추천이 아니라 검색 의도와 검증 가능성을 기준으로 한다.

## 7. 종목 검색 결과

각 종목 결과에 포함할 정보:

- 종목명
- 종목 코드
- 시장
- 기업명
- 업종 또는 산업
- 가장 최근 공식 정보
- 확인 상태
- 관심 종목 여부
- Analysis 존재 여부
- 마지막 확인 시점
- 다음 행동

### Primary CTA

- 종목 보기

### Secondary CTA

- 관심 종목 추가
- 공식 근거 보기
- 분석 보기
- 분석 시작하기

### 표현 원칙

- Search 결과 안에서 매수·매도 CTA를 제공하지 않는다.
- 가격과 등락률은 보조 정보로만 둔다.
- “왜 이 결과가 나왔는지”를 짧게 설명한다.

예:

```text
삼성전자 005930 · KOSPI
반도체 · Samsung Electronics
새 공식 정보 2개 · Analysis 있음 · 관심 종목
마지막 확인 오늘 09:00
[종목 보기] [관심 종목 추가] [공식 근거 보기]
```

## 8. 기업 검색 결과

하나의 기업에 여러 Security가 존재할 수 있음을 고려한다.

포함:

- 기업명
- 대표 종목
- 상장 시장
- 주요 사업
- 관련 산업
- 연결된 종목
- 최근 공식 정보
- 관련 Analysis
- 상세 진입

### 기업과 종목의 구분

기업과 종목을 같은 것으로 취급하지 않는다.

사용자 화면에서는 다음처럼 쉽게 구분한다.

```text
기업: Samsung Electronics
대표 종목: 삼성전자 005930 · KOSPI
연결 종목: 보통주, 우선주, 해외 관련 티커 후보
```

### 권장 행동

- 대표 종목 보기
- 관련 종목 보기
- 공식 정보 보기
- 관련 Analysis 보기

기업 검색 결과는 내부 Domain의 Company와 Security 분리를 유지하되, 사용자에게 과도한 금융 시스템 용어를 노출하지 않는다.

## 9. 테마 검색 결과

테마는 급등 테마 목록처럼 보이면 안 된다.

포함:

- 테마명
- 테마 설명
- 관련 종목
- 최근 공식 정보
- 아직 미확인 내용
- 관련 시장
- 관련 Analysis
- 상세 진입

### 금지 표현

- 테마 순위
- 기대수익
- 추천 종목
- 급등 테마
- 상승 유망 테마

### 권장 표현

- 관련 공식 정보
- 확인 필요한 내용
- 연결된 종목
- 관련 시장
- 기존 Analysis

테마 검색 결과는 Market 또는 Theme 상세 후보로 이어진다. Search 안에서 테마의 전체 흐름을 설명하지 않는다.

## 10. Evidence 검색 결과

공식 정보 검색은 DATE Search의 핵심 차별점이다.

포함:

- Evidence 제목
- 유형
- 공식 출처
- 공개 시각
- 확인 상태
- 정정 여부
- 관련 종목
- 관련 기업
- 확인 가능한 사실
- Evidence 상세 진입

### 표현 원칙

- 뉴스 검색 결과처럼 자극적인 제목 중심으로 만들지 않는다.
- 공식 출처와 공개 시각을 제목 가까이에 둔다.
- 정정 정보는 결과 목록에서도 분명히 표시한다.
- 확인 가능한 사실은 한 문장만 요약한다.
- 확인할 수 없는 내용은 상세에서 확인하게 한다.

### Primary CTA

- 공식 근거 확인하기

### Secondary CTA

- 관련 종목 보기
- 이 근거를 분석에 담기

Search는 Evidence의 전체 원문, 사실 검증, 해석 범위를 반복하지 않는다.

## 11. Analysis 검색 결과

사용자의 기존 Analysis 검색을 지원한다.

포함:

- Analysis 제목
- 대표 종목
- 상태
- 마지막 수정 시각
- 새 Evidence 여부
- 재검토 필요 여부
- 현재 질문
- Analysis 상세 진입

### 표현 원칙

- Search 안에서 Analysis를 편집하지 않는다.
- Analysis 상태와 System Attention을 간단히 보여준다.
- 새 Evidence가 있으면 “새 근거 검토 필요”처럼 검토 행동으로 표현한다.

### Primary CTA

- 분석 이어서 보기

### Secondary CTA

- 관련 종목 보기
- 새 근거 보기
- 달라진 내용 보기

Analysis가 없는 종목 결과에서는 “분석 시작하기”를 제공할 수 있다. 다만 Search가 Analysis 작성 화면을 대신하지 않는다.

## 12. Watchlist 연결

Search 결과에서 관심 종목을 추가할 수 있다.

### Low-Fi 권장 흐름

1. 관심 종목 추가
2. 관심 이유 선택
3. 다음 확인 시점 선택
4. 추적 시작

### 즉시 추가 vs Stock Detail 경유

현재 권장안:

- 검색 결과에서 빠른 관심 추가를 허용한다.
- 관심 이유와 다음 확인 시점은 간단 선택으로 제한한다.
- 자세한 추적 설정은 Watchlist 또는 Stock Detail에서 이어서 한다.

대안:

- 모든 관심 추가를 Stock Detail에서만 허용한다.

보류 이유:

- Search는 빠른 발견이 목적이므로 관심 추가 진입은 필요하다. 다만 Search 안에서 긴 설정을 요구하면 Search가 Watchlist 설정 화면처럼 복잡해진다.

### 피할 것

- 과도한 Modal
- 복잡한 Wizard
- 매수 후보처럼 보이는 관심 이유 입력
- AI 자동 분석 생성

Watchlist는 선택한 대상을 지속 추적하고, Search는 대상을 발견해 Watchlist 추가로 넘기는 역할이다.

## 13. Analysis 시작 연결

종목 또는 Evidence 결과에서 다음 행동을 제공할 수 있다.

- 분석 시작하기
- 기존 분석 보기
- 이 근거를 분석에 담기

### 권장 정책

종목 결과:

- 기존 Analysis가 있으면 “분석 보기”
- Analysis가 없으면 “분석 시작하기”

Evidence 결과:

- “이 근거를 분석에 담기”
- 기존 Analysis 선택은 Analysis 진입 후 처리

### 책임 경계

Search는 Analysis 작성 화면을 대신하지 않는다.

Search에서 할 수 있는 것:

- Analysis 존재 여부 표시
- 기존 Analysis로 이동
- 새 Analysis 시작 진입
- Evidence를 Analysis로 보낼 수 있는 진입 제공

Search에서 하지 않을 것:

- Analysis 내용 편집
- 판단 변경 조건 작성
- 사용자 해석 작성
- AI 자동 분석 생성

- 기업 결과 없음
- 테마 결과 없음
- Evidence 결과 없음
- Analysis 결과 없음

- 알 수 없는 코드
- 비로그인 상태

### 결과 없음 행동

제공할 행동:

- 검색어 다시 확인
- 종목 코드로 검색
- 시장에서 찾기
- 공식 근거에서 찾기
- 최근 본 항목 확인

### 원칙

- 존재하지 않는 종목을 임의로 생성하지 않는다.
- 추천 종목을 대신 보여주지 않는다.
- “검색 결과 없음”을 기술 오류처럼 표현하지 않는다.
- 공식 Evidence가 없는 경우 “공식 정보 없음”과 “시장 관찰만 있음”을 구분한다.

예:

```text
검색어와 정확히 일치하는 종목을 찾지 못했습니다.
종목 코드로 다시 검색하거나 시장에서 관련 종목을 찾아볼 수 있습니다.
```

## 19. Search와 다른 화면의 책임 구분

### Home

Home은 오늘 먼저 볼 내용을 안내한다.

Search와의 차이:

- Home은 사용자가 검색하기 전 오늘 시장을 이해하게 한다.
- Search는 사용자가 찾고 싶은 대상이 있을 때 빠르게 이동하게 한다.

### Market

Market은 시장 흐름을 탐색한다.

Search와의 차이:

- Market은 넓은 탐색 화면이다.
- Search는 특정 검색어를 기준으로 대상을 좁힌다.

### Stock Detail

Stock Detail은 특정 종목을 이해한다.

Search와의 차이:

- Search는 종목을 찾고 Stock Detail로 이동한다.
- Stock Detail은 종목의 현재 상태, 공식 근거, 관련 관계를 보여준다.

### Evidence

Evidence는 공식 정보를 검증한다.

Search와의 차이:

- Search는 Evidence를 찾고 제목, 출처, 공개 시각, 확인 상태만 요약한다.
- Evidence Detail은 확인 가능한 사실과 확인할 수 없는 내용을 검증한다.

### Analysis

Analysis는 사용자 판단 구조를 관리한다.

Search와의 차이:

- Search는 Analysis를 찾고 상태와 현재 질문만 요약한다.
- Analysis는 공식 사실, 사용자 해석, 미확인 내용, 판단 변경 조건을 관리한다.

### Changes

Changes는 이전 상태 이후 변화를 비교한다.

Search와의 차이:

- Search는 Changes 항목을 찾고 상세 비교로 이동한다.
- Changes는 Before / After와 재검토 이유를 담당한다.

### Watchlist

Watchlist는 선택한 대상을 지속 추적한다.

Search와의 차이:

- Search는 관심 대상으로 추가할 종목을 발견한다.
- Watchlist는 관심 이유, 다음 확인 시점, 새 공식 정보, Analysis 상태를 관리한다.

### Search

Search는 사용자가 원하는 대상을 발견하고 적절한 상세 화면으로 연결한다.

Search가 상세 화면의 정보를 전부 반복하지 않게 한다.

## 20. DATE 차별점

### 증권사 종목 검색과의 차이

증권사 검색은 보통 종목 진입과 매매 행동으로 이어진다. DATE Search는 종목, 공식 Evidence, Analysis, Watchlist 연결을 함께 보여주며 매수·매도 행동으로 이어지지 않는다.

### 네이버증권 검색과의 차이

네이버증권 검색은 종목, 뉴스, 시세 접근성이 강하다. DATE Search는 공식 출처, 확인 상태, 기존 Analysis, 다음 Research 행동을 함께 보여준다.

### 뉴스 검색과의 차이

뉴스 검색은 기사 소비 중심이다. DATE Search는 공식 Evidence와 공개 시각, 확인 상태를 우선한다.

### 공시 검색과의 차이

공시 검색은 문서 검색에 강하다. DATE Search는 공시가 어떤 종목, Analysis, Watchlist, Changes와 연결되는지 보여준다.

### 일반 사이트 통합 검색과의 차이

일반 검색은 모든 콘텐츠를 같은 목록으로 섞는다. DATE Search는 종목, 기업, Evidence, Analysis의 책임을 구분해 다음 행동을 제시한다.

### AI 검색과의 차이

AI 검색은 답변 생성이 결론처럼 보일 수 있다. DATE Search는 검색 결과와 공식 근거, 사용자 판단 구조로 이어지는 진입만 제공한다.

### DATE Search 차별점

- 종목과 기업 분리
- 공식 Evidence 직접 검색
- 확인 상태 표시
- Analysis 존재 여부 표시
- Watchlist 연결
- 검색 결과에서 다음 Research 행동 제시
- 추천이 아닌 발견과 검증 중심

## 21. North Star

Search의 성공은 사용자가 많은 결과를 본 것이 아니다.

성공한 Search는 사용자가 다음을 빠르게 수행하게 한다.

- 찾는 대상을 발견한다.
- 그 대상이 종목, 기업, 테마, Evidence, Analysis 중 무엇인지 이해한다.
- 무엇이 공식적으로 확인됐는지 확인한다.
- 관심 종목, Analysis, Evidence, Changes 중 적절한 다음 화면으로 이동한다.

Search는 정보 소비량을 늘리는 화면이 아니라 발견 후 검증과 판단 준비로 이어지는 진입점이다.

## 22. Open Questions

### 1. 검색 기본 대상은 종목으로 둘 것인가?

현재 권장안:

- 기본 대상은 종목으로 둔다.

대안:

- 통합 검색 결과를 모든 유형 동일 위계로 보여준다.

보류 이유:

- 한국 사용자는 검색창에서 종목명과 종목 코드를 먼저 기대하지만, DATE의 Evidence 검색 차별점도 함께 살려야 한다.

### 2. 종목과 기업 결과를 같은 영역에 둘 것인가?

현재 권장안:

- 구분하되, 정확 일치에서는 대표 종목과 기업 정보를 가까이 둔다.

대안:

- 종목과 기업을 하나의 결과로 합친다.

보류 이유:

- 하나의 기업에 여러 Security가 존재할 수 있어 장기적으로 혼동이 생긴다.

### 3. Evidence 검색을 기본 검색에 포함할 것인가?

현재 권장안:

- 포함한다.

대안:

- Evidence 전용 검색으로 분리한다.

보류 이유:

- DATE Search의 차별점은 공식 Evidence 직접 검색이지만, 결과가 많아지면 종목 검색 경험을 방해할 수 있다.

### 4. 초성 검색을 지원할 것인가?

현재 권장안:

- 후속 구현에서 지원한다.

대안:

- 정확 일치와 부분 일치만 지원한다.

보류 이유:

- 한국 사용자 기대가 높지만 검색 엔진 구현 범위와 품질 검증이 필요하다.

### 5. 한글 기업명과 영문 티커 우선순위는 어떻게 둘 것인가?

현재 권장안:

- 정확 일치 기준으로 동등하게 처리하고, 국내 종목 코드는 6자리 숫자 우선으로 해석한다.

대안:

- 한국어 결과를 항상 우선한다.

보류 이유:

- 미국 관련 종목과 국내 종목이 함께 쓰이는 흐름에서 영문 티커 검색도 중요하다.

### 6. 최근 검색과 최근 본 항목을 함께 보여줄 것인가?

현재 권장안:

- 함께 보여주되 최근 본 항목을 더 우선한다.

대안:

- 최근 검색어만 보여준다.

보류 이유:

- DATE는 검색어보다 사용자가 실제로 확인한 Evidence, Analysis, 종목 맥락이 더 중요하다.

### 7. 인기 검색어를 제공할 것인가?

현재 권장안:

- Low-Fi에서는 보조 후보로만 두고 기본 노출은 하지 않는다.

대안:

- 검색 전 상태에 인기 검색어를 제공한다.

보류 이유:

- 인기 검색어는 추천이나 급등 종목처럼 보일 위험이 있다.

### 8. 관심 종목을 검색 결과에서 바로 추가할 것인가?

현재 권장안:

- 바로 추가할 수 있게 하되 간단 선택으로 제한한다.

대안:

- Stock Detail을 반드시 거치게 한다.

보류 이유:

- 빠른 추가가 유용하지만 Search가 Watchlist 설정 화면처럼 복잡해지면 안 된다.

### 9. Analysis 시작을 Search에서 허용할 것인가?

현재 권장안:

- 허용하되 Analysis 작성은 Analysis 화면에서 한다.

대안:

- Analysis 시작은 Stock Detail 또는 Evidence Detail에서만 허용한다.

보류 이유:

- Search에서 바로 시작하면 빠르지만 사용자가 공식 정보 확인 없이 분석을 시작할 수 있다.

### 10. 검색 결과 우선순위에 사용자 맥락을 얼마나 반영할 것인가?

현재 권장안:

- 관심 종목, 기존 Analysis, 최근 확인 항목을 반영한다.

대안:

- 검색어 일치도만 사용한다.

보류 이유:

- 사용자 맥락은 유용하지만 개인화가 추천처럼 보이지 않게 표현해야 한다.

### 11. 테마 검색 결과를 추천처럼 보이지 않게 하는 기준은 무엇인가?

현재 권장안:

- 테마 설명, 관련 공식 정보, 미확인 내용, 관련 종목 수를 중심으로 표시한다.

대안:

- 테마 인기도나 상승률 중심으로 표시한다.

보류 이유:

- 상승률 중심은 급등 테마 추천처럼 보일 수 있다.

### 12. 공식 Evidence와 뉴스 검색을 분리할 것인가?

현재 권장안:

- 공식 Evidence를 기본 검색에 포함하고, 뉴스는 후속 보조 정보로 분리한다.

대안:

- 공식 정보와 뉴스를 같은 검색 결과에 섞는다.

보류 이유:

- 뉴스와 공식 Evidence가 같은 위계로 보이면 DATE의 공식성 원칙이 흐려진다.

### 13. 비로그인 사용자의 최근 검색을 로컬에 보존할 것인가?

현재 권장안:

- Low-Fi에서는 보존하지 않고 세션 예시만 둔다.

대안:

- 로컬 저장을 허용한다.

보류 이유:

- 개인정보 안내, 삭제, 로그인 후 동기화 정책이 필요하다.

### 14. Search URL에 query를 반영할 것인가?

현재 권장안:

- 결과 화면에서는 query를 URL에 반영한다.

대안:

- 입력 상태를 URL에 반영하지 않는다.

보류 이유:

- 공유와 뒤로가기에는 URL 반영이 좋지만, 개인정보가 포함될 수 있는 검색어는 주의가 필요하다.

### 15. 결과 없음에서 어떤 대안을 우선 제시할 것인가?

현재 권장안:

- 검색어 다시 확인, 종목 코드로 검색, 시장에서 찾기, 공식 근거에서 찾기 순으로 제시한다.

대안:

- 유사 종목이나 인기 종목을 먼저 제시한다.

보류 이유:

- 유사 종목 제시는 추천처럼 보일 수 있고, 존재하지 않는 종목을 임의 생성하면 신뢰가 약해진다.

## 검증 기준

이 문서와 이후 Search 화면 설계는 다음 기준을 통과해야 한다.

- 기존 KR Experience 문서와 충돌하지 않는가?
- Watchlist와 Search 책임 경계가 명확한가?
- Market과 Search 책임 경계가 명확한가?
- Stock Detail, Evidence, Analysis 책임을 반복하지 않는가?
- 투자 추천, 매수·매도 유도, 수익 기회 표현이 없는가?
- 영어 UX 용어가 사용자 화면 문구로 남용되지 않는가?
- 인기 검색어와 테마 결과가 추천처럼 보이지 않는가?
- 공식 Evidence와 뉴스 또는 시장 관찰을 구분하는가?
- 모바일에서 검색 입력, 최근 맥락, 빠른 결과가 Bottom Navigation과 충돌하지 않는가?
