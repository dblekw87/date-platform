# KR Watchlist Experience Planner

## 문서 목적

이 문서는 KR Prototype B의 관심 목록 화면을 구현하기 전 경험 구조를 정의한다.

이번 문서는 코드, route, component, wireframe, mock data, commit을 만들지 않는다. 목적은 사용자가 관심 대상을 단순히 저장하는 것이 아니라, 왜 보고 있는지, 무엇을 확인해야 하는지, 마지막 확인 이후 무엇이 달라졌는지, 어떤 분석과 투자 근거가 연결되어 있는지 지속적으로 추적하는 경험을 설계하는 것이다.

Prototype A의 Monitoring 또는 Watchlist 화면을 번역하거나 복사하지 않는다. KR Watchlist는 한국 투자자가 종목을 계속 지켜볼 때 필요한 이유, 공식 정보, 변화, 분석 상태, 다음 확인 항목을 관리하는 화면이다.

## 1. Watchlist Product Goal

### Watchlist는 왜 존재하는가

Watchlist는 사용자가 계속 추적할 대상을 유지하기 위해 존재한다.

DATE의 Watchlist는 즐겨찾기 목록, 시세 테이블, 가격 알림 목록이 아니다. 관심 목록에 들어온 대상은 사용자가 “나중에 다시 볼 이유가 있는 대상”이다. 따라서 Watchlist는 가격보다 추적 이유, 새 공식 정보, 기존 분석 여부, 마지막 확인 이후 변화, 다음 확인 항목을 먼저 보여줘야 한다.

### 사용자는 왜 종목을 관심 목록에 추가하는가

사용자는 다음 이유로 종목을 관심 목록에 추가한다.

- 공식 공시나 기업 발표를 기다린다.
- 실적 발표, 정책 발표, 규제 변화 같은 확인 시점이 있다.
- 기존 Analysis에서 아직 확인되지 않은 내용이 남아 있다.
- 판단 변경 조건과 연결된 정보가 나올 가능성이 있다.
- 관련 기업 또는 공급망 발표를 계속 확인해야 한다.
- 시장에서 발견한 종목을 나중에 다시 검토하려 한다.
- 단순히 가격을 보는 것이 아니라 근거와 변화 흐름을 놓치지 않으려 한다.

관심 추가 이유는 추천 근거나 매수 이유가 아니다. 관심 이유는 사용자가 이 대상을 계속 확인해야 하는 관리 목적이다.

### Watchlist를 본 뒤 확인해야 하는 것

사용자는 Watchlist를 본 뒤 다음 질문에 답할 수 있어야 한다.

1. 내가 왜 이 대상을 보고 있는가?
2. 마지막 확인 이후 새 공식 정보가 있는가?
3. 정정되거나 철회된 공식 정보가 있는가?
4. 기존 Analysis가 있는가?
5. 기존 Analysis를 다시 봐야 하는가?
6. 판단 변경 조건에 접근했거나 충족된 항목이 있는가?
7. 아직 확인되지 않은 내용이 유지되는가?
8. 다음에 언제, 무엇을 확인해야 하는가?

### 핵심 목표

- 관심 대상 유지
- 추적 이유 기록
- 새 공식 정보 발생 확인
- 기존 Analysis 존재 여부 확인
- 마지막 확인 이후 변화 확인
- 다음 확인 항목 관리

Watchlist의 성공은 종목 수가 많아지는 것이 아니다. 사용자가 각 관심 대상의 추적 이유와 다음 확인 행동을 명확히 이해하는 것이다.

## 2. 다른 화면과의 책임 구분

### Home

Home은 오늘 먼저 볼 변화를 안내한다.

Watchlist와의 차이:

- Home은 첫 진입에서 오늘 시장의 핵심 변화를 이해하게 한다.
- Watchlist는 사용자가 이미 선택한 관심 대상을 지속적으로 추적한다.
- Home은 “오늘 무엇을 먼저 볼 것인가”를 묻고, Watchlist는 “내가 계속 보고 있는 대상에서 무엇을 확인해야 하는가”를 묻는다.

### Market

Market은 시장 전체를 탐색한다.

Watchlist와의 차이:

- Market은 종목, 테마, 시장 흐름을 넓게 발견하는 화면이다.
- Watchlist는 사용자가 선택한 대상의 추적 상태를 관리한다.
- Market은 대상 발견을 담당하고, Watchlist는 발견 이후의 지속 확인을 담당한다.

### Stock Detail

Stock Detail은 특정 종목의 현재 상태를 이해하는 화면이다.

Watchlist와의 차이:

- Stock Detail은 종목명, 코드, 시장, 현재 변화, 관련 근거, 연결 관계를 보여준다.
- Watchlist는 여러 관심 종목 중 어디를 먼저 다시 봐야 하는지 알려준다.
- Stock Detail은 현재 상태 중심이고, Watchlist는 추적 상태 중심이다.

### Evidence

Evidence는 공식 정보를 검증한다.

Watchlist와의 차이:

- Evidence는 공식 출처, 공개 시각, 확인 가능한 사실, 확인할 수 없는 내용을 검증한다.
- Watchlist는 관심 대상에 새 공식 정보가 있는지와 확인 상태만 요약한다.
- Watchlist 안에서 Evidence 원문이나 전체 검증 구조를 반복하지 않는다.

### Analysis

Analysis는 판단 구조를 관리한다.

Watchlist와의 차이:

- Analysis는 공식 사실, 시장 관찰, 사용자 해석, 가설, 미확인 내용, 판단 변경 조건을 관리한다.
- Watchlist는 관심 대상에 연결된 Analysis 존재 여부와 재검토 필요 여부를 보여준다.
- Watchlist는 Analysis 내용을 편집하지 않고 판단 변경 조건을 소유하지 않는다.

### Changes

Changes는 이전 상태 이후 달라진 내용을 비교한다.

Watchlist와의 차이:

- Changes는 무엇이 달라졌고 왜 다시 봐야 하는지 비교한다.
- Watchlist는 변화가 있다는 사실과 추적 우선순위를 알려준다.
- Watchlist에서 Before / After 비교를 다시 구현하지 않는다.

### Watchlist

Watchlist는 관심 대상을 지속적으로 추적한다.

책임:

- 관심 대상 유지
- 관심 추가 이유 관리
- 마지막 확인과 다음 확인 시점 표시
- 새 공식 정보 수와 미확인 내용 수 표시
- 연결된 Analysis 상태 표시
- Changes, Evidence, Analysis로 이동할 우선순위 제공

### Journal

Journal은 과거 판단과 행동을 보존한다.

Watchlist와의 차이:

- Journal은 특정 시점의 판단과 행동을 보존한다.
- Watchlist는 현재 계속 추적할 대상과 다음 확인 행동을 관리한다.
- 추적 종료 후에도 과거 Analysis와 Changes 기록은 Journal 또는 기록 영역에서 보존될 수 있다.

## 3. Watchlist 기본 단위

### 기본 단위 후보

#### 종목

장점:

- 한국 투자자가 가장 익숙한 관심 단위이다.
- 종목명, 종목 코드, 시장을 기준으로 추적하기 쉽다.
- Stock Detail, Analysis, Changes와 자연스럽게 연결된다.

한계:

- 기업 단위 공시나 테마 단위 변화가 종목 여러 개에 걸칠 수 있다.

#### 기업

장점:

- 기업 발표, 실적, 공급망 변화 추적에 적합하다.
- 내부 Domain에서 Company와 Security를 분리하기 좋다.

한계:

- 사용자 화면에서는 종목명과 종목 코드 기대가 더 강하다.

#### 테마

장점:

- 반도체, 배터리, AI 인프라처럼 여러 종목을 함께 추적하기 좋다.

한계:

- 관심 목록이 시장 탐색 화면처럼 넓어질 수 있다.
- 종목별 Analysis 상태가 흐려질 수 있다.

#### ETF

장점:

- 시장 또는 테마를 상품 단위로 추적할 수 있다.

한계:

- 개별 종목 Analysis와 같은 구조로 다루기 어렵다.

#### 시장

장점:

- 환율, 금리, 지수 같은 기준점을 추적하기 좋다.

한계:

- Market의 책임과 겹칠 수 있다.

#### Evidence

장점:

- 특정 공시나 발표를 나중에 다시 보기 좋다.

한계:

- Evidence는 관심 대상이 아니라 공식 정보 원천이다.
- Watchlist가 Evidence 북마크 목록처럼 보일 위험이 있다.

#### Analysis

장점:

- 사용자 판단 구조를 기준으로 재검토 대상을 추적하기 좋다.

한계:

- Watchlist가 Analysis 목록처럼 보일 수 있다.

### 권장안

기본 단위는 종목 중심으로 둔다.

권장 구조:

```text
관심 항목
├─ 기본 대상: 종목
├─ 연결 기업
├─ 보조 추적 단위: 테마
├─ 보조 추적 단위: ETF
├─ 연결 Analysis
├─ 연결 Changes
└─ 연결 Evidence
```

보조 추적 단위는 기업, 테마, ETF, Analysis로 둔다. Evidence는 관심 목록 대상이 아니라 관심 항목에 연결된 공식 정보로 처리한다.

## 4. 관심 추가 이유

### 관리 여부

관심 추가 이유는 관리한다.

다만 처음 추가할 때 긴 입력을 요구하지 않는다. Low-Fi 기준에서는 이유 선택을 먼저 제공하고, 직접 입력은 선택 사항으로 둔다.

### 이유 후보

- 공식 공시 대기
- 실적 발표 확인
- 규제 변화 확인
- 공급망 변화 확인
- 관련 기업 발표 확인
- 가설 검증
- Analysis 재검토
- 단순 관심

### 표현 원칙

- 관심 이유는 매수 이유처럼 보이면 안 된다.
- “상승 기대”, “매수 후보”, “추천 근거” 같은 표현은 사용하지 않는다.
- 이유는 사용자가 확인해야 할 정보의 성격으로 표현한다.

### 입력 구조

권장 구조:

1. 관심 이유 선택
2. 직접 입력 선택 가능
3. 다음 확인 시점 선택
4. 연결할 Analysis 선택 가능

Low-Fi에서는 선택 이유 1개와 직접 메모 1개까지 허용한다. 여러 이유를 동시에 고르는 구조는 후속 단계에서 검토한다.

## 5. Watchlist Item 구조

각 관심 항목은 다음 정보를 가진다.

| 정보 | 역할 | 표시 원칙 |
| --- | --- | --- |
| 종목명 | 기본 대상 식별 | 가장 먼저 표시 |
| 종목 코드 | 종목 식별 | 종목명 가까이에 표시 |
| 시장 | KOSPI, KOSDAQ 등 | 보조 Metadata |
| 관심 추가 이유 | 왜 추적하는지 | 가격 이유가 아니라 확인 이유 |
| 마지막 확인 시점 | 사용자가 마지막으로 확인한 기준 | 변화 수와 함께 표시 |
| 마지막 공식 정보 시점 | 마지막 Evidence 공개 시각 | 공식 정보 기준점 |
| 새 공식 정보 수 | 새 Evidence 요약 | 공식 출처 기반 |
| 미확인 내용 수 | 아직 확인되지 않은 항목 | Analysis와 연결 가능 |
| 연결된 Analysis 수 | 기존 분석 존재 여부 | 상세는 Analysis로 이동 |
| Analysis 상태 | 재검토 필요 여부 | 편집하지 않음 |
| 판단 변경 조건 접근 여부 | 조건과 가까워졌는지 | 조건 내용 상세는 Analysis에서 확인 |
| 다음 확인 시점 | 다시 볼 날짜 또는 장 구간 | 알림과 분리 |
| 다음 확인 이유 | 무엇을 확인할지 | 짧은 문장 |
| 현재 추적 상태 | 확인 필요, 대기, 보류 등 | 매매 상태 금지 |
| 가장 중요한 변화 | 변화 요약 1개 | 상세 비교는 Changes로 이동 |
| 관련 Evidence | 대표 근거와 출처 | 전체 내용 반복 금지 |
| 다음 행동 | 사용자가 할 수 있는 행동 | 상태별 CTA 1개 중심 |
| 가격과 등락률 | 보조 정보 | 낮은 위계, 우선순위 기준 아님 |

가격과 등락률은 보조 정보로만 둔다. 가격 변화가 새 공식 정보, 판단 변경 조건, Analysis 재검토와 연결되지 않으면 Watchlist 우선순위의 근거로 사용하지 않는다.

## 6. Watchlist 상태

Watchlist 상태는 매매 행동이나 수익 결과가 아니라 추적 진행 상태를 나타낸다.

| 상태 | 의미 | 다음 행동 |
| --- | --- | --- |
| 확인 필요 | 사용자가 먼저 봐야 할 항목이 있음 | 관심 변화 확인 |
| 새 공식 정보 있음 | 마지막 확인 이후 새 Evidence가 있음 | 새 근거 확인 |
| Analysis 재검토 필요 | 연결된 Analysis에 영향 가능성이 있음 | 분석 다시 보기 |
| 미확인 내용 유지 | 아직 공식 확인되지 않은 내용이 남아 있음 | 필요한 출처 확인 |
| 다음 확인 대기 | 정한 확인 시점 전까지 대기 | 다음 확인 시점 유지 |
| 현재 변화 없음 | 마지막 확인 이후 중요한 변화 없음 | 필요 시 종목 보기 |
| 추적 보류 | 사용자가 일시적으로 우선순위를 낮춤 | 추적 재개 또는 유지 |
| 추적 종료 | 더 이상 추적하지 않기로 함 | 기록 보존 후 숨김 |

금지 상태:

- 매수
- 매도
- 보유
- 수익
- 손실
- 추천
- 상승 후보
- 매집

상태는 시스템이 제안할 수 있지만, 추적 보류와 추적 종료는 사용자가 직접 결정하는 흐름을 우선한다.

## 7. Changes 연결

Watchlist에서 변화 전체를 다시 구현하지 않는다.

Watchlist에 포함할 Changes 요약:

- 마지막 확인 이후 새 변화 수
- 가장 중요한 변화 1개
- 정정 정보 여부
- Analysis 영향 여부
- Changes 상세 이동

표현 예:

```text
마지막 확인 이후 3개 변화
정정된 공식 정보 1개가 있어 먼저 확인이 필요합니다.
```

Primary CTA 후보:

- 달라진 내용 확인하기

Secondary CTA 후보:

- 종목에서 보기
- 연결된 근거 보기

책임 경계:

- Changes는 비교와 재검토 이유를 담당한다.
- Watchlist는 변화가 있다는 사실과 추적 우선순위를 알려준다.
- Watchlist는 Before / After 구조를 반복하지 않는다.

## 8. Analysis 연결

각 Watchlist Item은 Analysis 관계를 표시한다.

포함 정보:

- 연결된 Analysis 존재 여부
- 연결된 Analysis 수
- 대표 Analysis 제목
- Analysis 상태
- 마지막 수정 시각
- 새 근거 검토 필요 여부
- 판단 변경 조건 접근 여부
- Analysis 상세 이동

Analysis가 있는 경우:

- “연결된 분석이 있습니다.”
- “새 공식 정보가 기존 분석과 연결됩니다.”
- “판단 변경 조건에 가까워졌습니다.”

Analysis가 없는 경우:

- “연결된 분석이 아직 없습니다.”
- Primary 또는 Secondary CTA: 분석 시작하기

원칙:

- Watchlist 안에서 Analysis 내용을 편집하지 않는다.
- Analysis 상태를 단순 요약으로만 표시한다.
- AI 자동 분석 생성은 금지한다.
- “분석 시작하기”는 사용자가 직접 판단 구조를 만들기 위한 진입이다.

## 9. Evidence 연결

각 관심 대상은 새 공식 Evidence 상태를 보여준다.

포함 정보:

- 새 Evidence 수
- 대표 Evidence 제목
- 공식 출처
- 공개 시각
- 확인 상태
- 정정 여부
- Evidence 상세 이동

표현 원칙:

- 공식 출처와 공개 시각을 제목 가까이에 둔다.
- 정정 정보는 우선 표시한다.
- Watchlist 안에서 Evidence 전체 내용을 반복하지 않는다.
- Evidence가 없는 경우 가격 반응이나 시장 관찰을 공식 사실처럼 표현하지 않는다.

Evidence는 관심 목록의 기본 대상이 아니다. Evidence는 종목, 기업, 테마, Analysis에 연결된 공식 정보로 다룬다.

## 10. 추적 우선순위

Watchlist 정렬 기준은 등락률이나 거래량이 아니라 공식성, 기존 판단 영향도, 사용자가 정한 확인 시점을 기준으로 한다.

### Priority 1

가장 먼저 확인해야 하는 항목.

포함:

- 정정된 공식 정보
- 철회 또는 삭제된 공식 정보
- 판단 변경 조건 충족 또는 접근
- Analysis 재검토 필요

문구:

- 먼저 확인해야 하는 관심 대상입니다.
- 기존 분석을 다시 볼 필요가 있습니다.

### Priority 2

공식 정보가 새로 추가되었거나 기존 미확인 내용이 해소된 항목.

포함:

- 새 공식 Evidence
- 기존 미확인 내용 공식 확인
- 관련 기업 공식 발표

문구:

- 새 공식 정보가 추가됐습니다.
- 이전에 확인하지 못했던 내용이 공식 정보와 연결됐습니다.

### Priority 3

사용자가 정한 확인 시점이나 관련 대상 변화 때문에 다시 볼 항목.

포함:

- 다음 확인 시점 도래
- 관련 기업 공식 발표
- 연결 테마의 공식 정보 추가

문구:

- 다시 확인하기로 한 시점입니다.
- 관련 대상의 공식 발표가 추가됐습니다.

### Priority 4

현재 큰 변화가 없거나 참고 추적 중인 항목.

포함:

- 현재 변화 없음
- 참고 추적
- 추적 보류 전 상태

문구:

- 마지막 확인 이후 중요한 공식 변화는 없습니다.

단순 등락률, 거래량, 인기 검색, 상승률만으로 우선순위를 정하지 않는다.

## 11. Grouping

한 화면에서 모든 Grouping을 동시에 노출하지 않는다.

### 기본 Grouping 후보

- 확인 필요
- 새 공식 정보
- Analysis 재검토
- 다음 확인 대기
- 현재 변화 없음

### 보조 Grouping 후보

- 시장
- 테마
- 사용자 지정 목록
- 관심 이유

### 권장안

기본 Grouping은 추적 상태 중심으로 둔다.

권장 순서:

1. 확인 필요
2. 새 공식 정보
3. Analysis 재검토
4. 다음 확인 시점 도래
5. 다음 확인 대기
6. 현재 변화 없음
7. 추적 보류 또는 종료

이유:

- Watchlist의 목적이 추적 우선순위 관리이기 때문이다.
- 시장이나 테마보다 “무엇을 먼저 확인해야 하는가”가 중요하다.
- Changes와 Analysis로 이어지는 행동이 명확해진다.

### 대안

사용자 지정 목록 중심:

- 반도체, 실적 발표 대기, 공급망처럼 사용자가 만든 목록을 먼저 보여준다.
- 장점은 개인 문맥이 강하다.
- 단점은 정정 정보나 Analysis 재검토 필요 항목이 목록 안에 묻힐 수 있다.

시장 중심:

- KOSPI, KOSDAQ, ETF 등으로 나눈다.
- 장점은 종목 관리에 익숙하다.
- 단점은 DATE의 공식 정보와 재검토 중심 차별점이 약해진다.

관심 이유 중심:

- 공시 대기, 실적 확인, 가설 검증 등으로 묶는다.
- 장점은 왜 보는지 명확하다.
- 단점은 같은 종목이 여러 이유에 걸칠 때 중복 관리가 필요하다.

Low-Fi 권장안은 추적 상태 Grouping을 기본으로 하고, 사용자 지정 목록은 별도 하단 영역 또는 필터로 제공한다.

## 12. 사용자 지정 목록

사용자가 Watchlist를 여러 목록으로 나누는 기능은 필요하다. 다만 과도한 폴더 시스템이나 태그 시스템은 피한다.

### 목록 예시

- 반도체
- 실적 발표 대기
- 공시 확인
- 공급망
- 미국 연관 종목
- 이번 주 확인

### Low-Fi 최소 구조

권장:

- 기본 목록 1개를 제공한다.
- 사용자는 짧은 이름의 사용자 지정 목록을 만들 수 있다.
- 하나의 관심 항목은 기본적으로 1개 사용자 목록에 속한다.
- 관심 이유는 목록과 별도로 유지한다.
- 목록은 우선 필터 또는 섹션 진입으로 제공하고, 복잡한 폴더 구조는 만들지 않는다.

대안:

- 하나의 종목을 여러 사용자 목록에 넣을 수 있게 한다.

보류 이유:

- 여러 목록 동시 소속은 유용하지만, Low-Fi에서는 이동, 제거, 중복 표시, 우선순위 계산이 복잡해진다.

## 13. 마지막 확인과 다음 확인

각 항목은 다음 시간 정보를 표시한다.

- 마지막 확인 시점
- 마지막 공식 정보 시점
- 다음 확인 시점
- 다음 확인 이유

### 마지막 확인 시점

마지막 확인 시점은 사용자가 관심 항목 또는 연결된 Changes, Evidence, Analysis를 확인한 기준 시점이다.

권장:

- “사용자 확인 기준”을 기본으로 둔다.
- 시스템이 자동으로 추정할 수 있지만, 사용자가 “확인함”을 선택한 시점을 우선한다.

### 마지막 공식 정보 시점

마지막 공식 정보 시점은 연결된 Evidence의 공개 시각 또는 정정 시각이다.

원칙:

- 사용자 확인 시점과 공식 정보 공개 시점을 분리한다.
- 공식 정보가 새로 공개됐지만 사용자가 보지 않은 상태를 명확히 표시한다.

### 다음 확인 시점

다음 확인 시점은 실제 알림 기능과 분리한다.

현재 Planner에서는 날짜, 장 구간, 상태 관리까지만 정의한다.

예:

- 2026-08-05 장 마감 후
- 다음 실적 발표일
- 후속 공시 확인 시점
- 관련 기업 발표 이후

### 다음 확인 이유

다음 확인 이유는 사용자가 무엇을 확인해야 하는지 짧게 설명한다.

예:

- 후속 공시에서 적용 범위 확인
- 실적 발표에서 매출 반영 여부 확인
- 관련 기업 공식 입장 확인

## 14. Desktop UX

Desktop은 종목 시세 테이블이 아니라 관심 대상 추적 흐름이어야 한다.

권장 구조:

1. Watchlist Hero
   - 확인 필요한 관심 대상 수
   - 새 공식 정보 수
   - Analysis 재검토 필요 수
   - 마지막 전체 확인 시점
   - Primary CTA

2. 가장 먼저 확인할 관심 대상
   - Priority 1 항목
   - 정정 정보, 판단 변경 조건 접근, Analysis 재검토 필요 표시
   - CTA: 달라진 내용 확인하기

3. 새 공식 정보 있음
   - 새 Evidence가 있는 항목
   - 공식 출처와 공개 시각
   - Evidence 상세 진입

4. Analysis 재검토 필요
   - 연결된 Analysis 상태
   - 마지막 수정 시각
   - 판단 변경 조건 접근 여부
   - Analysis 상세 진입

5. 다음 확인 시점 도래
   - 다음 확인 이유
   - 확인 예정 시점
   - 확인함 또는 다음 시점 변경 후보

6. 현재 변화 없음
   - 조용히 유지되는 추적 항목
   - 종목 보기 또는 관심 이유 수정

7. 사용자 지정 목록
   - 목록별 항목 수
   - 목록 진입
   - 과도한 폴더 탐색 금지

8. 추적 종료 또는 보류
   - 최근 보류 또는 종료한 항목
   - 기록 보존 안내

Desktop 원칙:

- 단일 세로 흐름을 기본으로 한다.
- Dashboard Grid를 남발하지 않는다.
- 고정 우측 Rail은 만들지 않는다.
- 긴 시세 테이블처럼 만들지 않는다.
- 가격과 등락률은 낮은 위계로 둔다.
- 관심 이유, 새 공식 정보, Analysis 상태, 다음 확인 시점이 row의 중심이어야 한다.

## 15. Mobile UX

Mobile 첫 화면에는 다음이 반드시 보여야 한다.

- 확인 필요한 관심 대상 수
- 새 공식 정보 수
- Analysis 재검토 필요 수
- 가장 먼저 확인할 종목
- Primary CTA

권장 흐름:

1. 가장 먼저 확인할 대상
2. 새 공식 정보 있음
3. Analysis 재검토 필요
4. 다음 확인 시점
5. 현재 변화 없음
6. 사용자 지정 목록

Mobile 원칙:

- 긴 표를 사용하지 않는다.
- Compact Row 중심으로 설계한다.
- 각 Row는 종목명, 관심 이유, 상태, 다음 행동을 우선 보여준다.
- 가격과 등락률은 필요할 때만 보조로 둔다.
- 기존 Bottom Navigation을 유지한다.
- 여러 상태 문구가 한 줄에 몰려 overflow가 나지 않게 줄바꿈을 허용한다.
- 첫 화면 Primary CTA는 하나만 강조한다.

```text
먼저 확인할 종목

```

## 16. CTA Strategy

Primary CTA는 현재 가장 중요한 상태에 따라 하나만 강조한다.

| 상황 | Primary CTA |
| --- | --- |
| 마지막 확인 이후 변화 있음 | 관심 변화 확인하기 |
| 새 공식 Evidence 있음 | 새 근거 확인하기 |
| Analysis 영향 있음 | 분석 다시 보기 |
| 정정 정보 있음 | 정정 내용 확인하기 |
| 다음 확인 시점 도래 | 확인 항목 보기 |

Secondary CTA:

- 종목 보기
- 관심 이유 수정하기
- 다음 확인 시점 설정하기
- 다른 목록으로 이동하기
- 추적 보류하기
- 관심 목록에서 제거하기
- 분석 시작하기
- 연결된 근거 보기

금지 CTA:

- 매수하기
- 매도하기
- 추천 종목 보기
- 상승 가능성 보기
- AI 분석 받기
- 목표가 확인하기
- 수익 기회 보기

CTA 문구는 사용자가 확인, 검토, 정리하는 행동으로 제한한다.

## 17. 관심 추가 흐름

사용자가 Stock Detail에서 관심 종목을 추가할 때의 흐름은 짧아야 한다.

### 전체 후보 흐름

1. 관심 종목 추가
2. 관심 이유 선택 또는 입력
3. 연결할 Analysis 선택
4. 다음 확인 시점 선택
5. 추적 시작

### Low-Fi 권장 흐름

Low-Fi에서는 다음까지 구현 대상으로 정의한다.

1. 관심 종목 추가
2. 관심 이유 선택
3. 다음 확인 시점 선택
4. 추적 시작

연결할 Analysis 선택은 선택 항목으로 둔다. 기존 Analysis가 있으면 제안하되, 사용자가 건너뛸 수 있어야 한다.

### 과도한 Modal 방지

권장:

- 1단계 Sheet 또는 Inline Panel에서 처리한다.
- 관심 이유와 다음 확인 시점을 한 화면에서 선택한다.
- 직접 입력은 펼쳐보기로 제공한다.

피할 것:

- 여러 단계 Modal
- 긴 설명 문구
- 투자 목적 또는 매수 이유 입력처럼 보이는 질문
- AI 자동 분석 생성 제안

## 18. 관심 제거와 추적 종료

관심 목록에서 제거하는 것과 추적 종료는 구분한다.

### 후보

- 관심 제거
- 추적 보류
- 추적 종료
- 기록으로 보존

### 권장 정책

#### 관심 제거

의미:

- 현재 Watchlist에서 더 이상 보지 않는다.

처리:

- 과거 Analysis와 Changes 기록은 삭제하지 않는다.
- 관심 이유와 다음 확인 설정은 보관 또는 삭제 후보로 둔다.

#### 추적 보류

의미:

- 당장은 우선순위를 낮추지만 나중에 다시 볼 수 있다.

처리:

- 보류 목록 또는 하단 영역에 유지한다.
- 새 정정 정보나 판단 변경 조건이 발생하면 다시 확인 필요로 올릴 수 있다.

#### 추적 종료

의미:

- 더 이상 이 대상을 추적하지 않기로 한다.

처리:

- 기록으로 보존하는 선택을 제공한다.
- 연결된 Analysis는 종료 또는 보관 후보가 될 수 있지만 자동 종료하지 않는다.
- 과거 Changes와 Analysis를 삭제하지 않는다.

원칙:

- 삭제는 사용자 데이터 손실처럼 느껴질 수 있으므로 “추적 종료”와 “관심 제거”를 명확히 구분한다.
- 과거 판단 구조는 보존을 우선한다.

## 19. Empty State

### 관심 종목 없음

문구:

- 아직 추적 중인 관심 대상이 없습니다.
- 시장이나 종목에서 계속 확인할 대상을 추가해보세요.

다음 행동:

- 종목 검색
- 시장에서 종목 보기

### 새 변화 없음

문구:

- 마지막 확인 이후 중요한 공식 변화는 없습니다.
- 다음 확인 시점에 다시 확인할 항목을 유지할 수 있습니다.

다음 행동:

- 다음 확인 항목 보기
- 시장 보기

### Analysis 없음

문구:

- 연결된 분석이 아직 없습니다.
- 이 종목을 왜 보고 있는지 질문으로 정리하면 다음 변화가 생겼을 때 다시 보기 쉽습니다.

다음 행동:

- 분석 시작하기
- 종목 보기

### Evidence 없음

문구:

- 이 관심 대상에 연결된 새 공식 정보는 아직 없습니다.
- 시장 관찰은 공식 근거와 구분해서 확인해야 합니다.

다음 행동:

- 종목 보기
- 시장 보기

### 모든 항목 확인 완료

문구:

- 확인할 관심 변화는 모두 정리됐습니다.
- 다음 확인 시점이 오면 다시 표시됩니다.

다음 행동:

- 다음 확인 시점 관리
- 현재 변화 없는 항목 보기

### 사용자 지정 목록 없음

문구:

- 아직 만든 목록이 없습니다.
- 자주 함께 보는 종목만 짧은 목록으로 묶을 수 있습니다.

다음 행동:

- 목록 만들기

### 알 수 없는 목록 접근

문구:

- 확인할 수 없는 관심 목록입니다.
- 전체 관심 목록에서 다시 선택할 수 있습니다.

다음 행동:

- 전체 관심 목록 보기
- 시장으로 이동

### 비로그인 상태

문구:

- 로그인 전에는 예시 관심 목록만 볼 수 있습니다.
- 내 관심 이유와 다음 확인 시점 저장은 로그인 후 제공됩니다.

다음 행동:

- 예시 관심 목록 보기
- 시장 둘러보기

비로그인 상태에서 저장 가능한 것처럼 보이면 안 된다.

## 20. Search와의 연결

Search는 Watchlist 추가를 위한 대상 발견을 담당한다.

연결 대상:

- 종목 검색
- 기업 검색
- 테마 검색
- 최근 본 종목
- Market에서 발견한 종목

### 책임 구분

Search:

- 대상을 찾는다.
- 종목, 기업, 테마 후보를 보여준다.
- 최근 본 대상과 시장에서 발견한 대상을 다시 찾게 한다.

Watchlist:

- 선택한 대상을 지속 추적한다.
- 관심 이유, 다음 확인 시점, 새 공식 정보, 연결 Analysis 상태를 관리한다.

### 추가 흐름

Search에서 바로 관심 추가를 허용할 수 있다.

권장:

- Search 결과에서 “관심 추가”를 제공한다.
- 추가 후 최소한 관심 이유 또는 다음 확인 시점 중 하나를 설정하게 한다.
- 자세한 설정은 Watchlist 또는 Stock Detail에서 이어서 할 수 있다.

보류:

- Search 결과에서 긴 관심 이유 입력까지 요구하는 흐름.

이유:

- Search는 빠른 발견이 목적이고, Watchlist는 추적 설정이 목적이다.

## 21. DATE 차별점

### 증권사 관심 종목과의 차이

증권사 관심 종목은 주로 가격, 등락률, 체결, 알림 중심이다. DATE Watchlist는 왜 이 대상을 보는지와 마지막 확인 이후 어떤 공식 정보가 달라졌는지를 중심으로 한다.

### 네이버 관심 종목과의 차이

네이버 관심 종목은 종목 접근성과 뉴스 소비에 강하다. DATE Watchlist는 공식 Evidence, Changes, Analysis 상태, 다음 확인 항목을 연결한다.

### 가격 알림 목록과의 차이

가격 알림은 특정 가격 조건 도달을 알려준다. DATE Watchlist는 가격만으로 우선순위를 정하지 않고, 공식 정보와 판단 변경 조건을 기준으로 다시 볼 항목을 제안한다.

### 일반 즐겨찾기와의 차이

일반 즐겨찾기는 다시 접근하기 위한 저장이다. DATE Watchlist는 추적 이유와 다음 확인 행동을 관리한다.

### 뉴스 구독과의 차이

뉴스 구독은 새 기사 소비 중심이다. DATE Watchlist는 공식 출처와 공개 시각이 확인된 Evidence를 우선한다.

### Notion 종목 목록과의 차이

Notion 목록은 사용자가 구조를 직접 만들어야 한다. DATE Watchlist는 관심 이유, 새 공식 정보, Changes, Analysis, 다음 확인 시점을 기본 구조로 제공한다.

### DATE Watchlist 차별점

- 관심 이유 관리
- 새 공식 정보 우선
- Changes 연결
- Analysis 상태 연결
- 판단 변경 조건 접근 표시
- 마지막 확인 / 다음 확인 관리
- 가격보다 근거와 재검토 중심

## 22. North Star

Watchlist의 성공은 사용자가 많은 종목을 추가한 것이 아니다.

성공한 Watchlist는 사용자가 다음을 명확하게 알게 한다.

- 왜 이 대상을 보고 있는가
- 마지막 확인 이후 무엇이 달라졌는가
- 새 공식 정보가 있는가
- 기존 Analysis를 다시 봐야 하는가
- 아직 확인되지 않은 내용은 무엇인가
- 다음에 무엇을 확인해야 하는가

Watchlist는 시세를 빠르게 소비하는 화면이 아니라 관심 대상을 잊지 않고 다시 검토하게 하는 추적 화면이다.

## 23. Open Questions

### 1. Watchlist 기본 단위는 종목으로 고정할 것인가?

현재 권장안:

- 기본 단위는 종목 중심으로 둔다.

대안:

- 기업, 테마, ETF, Analysis를 같은 수준의 기본 단위로 허용한다.

보류 이유:

- 한국 사용자는 종목명과 종목 코드를 기준으로 관심 목록을 이해하지만, 기업과 종목의 내부 Domain 분리는 유지해야 한다.

### 2. 테마와 ETF도 같은 목록에 둘 것인가?

현재 권장안:

- 테마와 ETF는 보조 추적 단위로 허용하되, 기본 목록에서는 종목과 구분해 표시한다.

대안:

- 종목, 테마, ETF를 완전히 같은 Row 구조로 둔다.

보류 이유:

- 테마와 ETF는 Evidence, Analysis, Changes 연결 방식이 종목과 다를 수 있다.

### 3. 관심 추가 이유를 필수로 받을 것인가?

현재 권장안:

- Low-Fi에서는 필수에 가깝게 권장하되 “단순 관심”을 선택할 수 있게 한다.

대안:

- 관심 이유 없이 바로 추가한다.

보류 이유:

- 이유 입력이 너무 강하면 빠른 추가가 어려워지고, 이유가 없으면 DATE Watchlist의 차별점이 약해진다.

### 4. 하나의 종목을 여러 사용자 목록에 넣을 수 있는가?

현재 권장안:

- Low-Fi에서는 하나의 종목은 기본적으로 하나의 사용자 지정 목록에 둔다.

대안:

- 하나의 종목을 여러 목록에 동시에 넣을 수 있게 한다.

보류 이유:

- 다중 목록은 유용하지만 중복 표시, 우선순위 정렬, 제거 정책이 복잡해진다.

### 5. 사용자 지정 목록은 몇 개까지 허용할 것인가?

현재 권장안:

- Low-Fi에서는 제한 숫자를 확정하지 않고, 소수의 짧은 목록을 전제로 설계한다.

대안:

- 목록 개수를 명시적으로 제한한다.

보류 이유:

- 실제 사용자가 목록을 몇 개 만드는지 검증 전에는 숫자를 고정하기 어렵다.

### 6. 마지막 확인 시점은 자동인가, 사용자 기준인가?

현재 권장안:

- 사용자 확인 기준을 기본으로 하고, 시스템 자동 추정은 보조로 둔다.

대안:

- 사용자가 항목을 열면 자동으로 마지막 확인 시점을 갱신한다.

보류 이유:

- 단순 열람과 실제 검토 완료는 다르다.

### 7. 다음 확인 시점은 알림과 연결할 것인가?

현재 권장안:

- 현재 Planner에서는 날짜와 상태 관리까지만 정의하고 알림과 분리한다.

대안:

- 다음 확인 시점을 바로 알림 예약과 연결한다.

보류 이유:

- 알림은 별도 Notification 책임과 겹칠 수 있고, 이번 범위가 아니다.

### 8. Analysis가 없는 관심 종목을 어떻게 보여줄 것인가?

현재 권장안:

- “연결된 분석 없음”을 명확히 표시하고 “분석 시작하기” CTA를 제공한다.

대안:

- Analysis가 없는 항목은 단순 관심 항목으로만 표시한다.

보류 이유:

- Analysis가 없더라도 공식 정보와 다음 확인 시점 추적은 가능해야 한다.

### 9. 가격 변동을 어디까지 보조 정보로 노출할 것인가?

현재 권장안:

- 종목 식별을 돕는 낮은 위계의 보조 정보로만 표시한다.

대안:

- 가격과 등락률을 Row 오른쪽 주요 정보로 둔다.

보류 이유:

- 가격 중심 배치는 증권사 관심 종목과 비슷해지고 DATE의 근거 중심 차별점이 약해진다.

### 10. 추적 보류와 관심 제거를 구분할 것인가?

현재 권장안:

- 구분한다.

대안:

- 제거 하나로 단순화한다.

보류 이유:

- 사용자는 당장 보지 않지만 기록과 조건은 유지하고 싶은 경우가 있다.

### 11. 관심 제거 시 과거 Changes와 Analysis는 유지할 것인가?

현재 권장안:

- 유지한다.

대안:

- 관심 제거와 함께 연결 데이터를 숨기거나 삭제한다.

보류 이유:

- 과거 판단과 변화 기록은 사용자 판단 맥락이므로 삭제하면 Journal과 Analysis의 신뢰가 약해진다.

### 12. 정렬 우선순위를 시스템이 제안할지 사용자가 고정할지

현재 권장안:

- 시스템이 공식 정보, 정정, Analysis 영향, 다음 확인 시점을 기준으로 제안한다.

대안:

- 사용자가 직접 고정 순서를 관리한다.

보류 이유:

- 직접 정렬은 개인화에 좋지만, 정정 정보나 재검토 필요 항목이 아래로 묻힐 수 있다.

### 13. Watchlist와 Changes의 중복 정보를 어디까지 허용할 것인가?

현재 권장안:

- Watchlist는 변화 수와 가장 중요한 변화 한 문장까지만 표시한다.

대안:

- Watchlist Item 안에서 Before / After 요약까지 보여준다.

보류 이유:

- Before / After는 Changes의 핵심 책임이다. Watchlist가 이를 반복하면 화면 목적이 흐려진다.

### 14. 비로그인 사용자는 로컬 관심 목록을 사용할 수 있는가?

현재 권장안:

- 비로그인 상태에서는 예시 관심 목록과 읽기 흐름만 제공하고 실제 저장은 제한한다.

대안:

- 로컬 관심 목록을 허용한다.

보류 이유:

- 로컬 저장은 유입에 좋지만 로그인 전후 동기화와 데이터 손실 안내가 필요하다.

### 15. 종목 검색에서 바로 관심 이유까지 입력하게 할 것인가?

현재 권장안:

- Search에서는 빠른 관심 추가를 제공하고, 관심 이유 입력은 간단 선택까지만 허용한다.

대안:

- Search 결과에서 관심 이유, 목록, 다음 확인 시점까지 모두 입력하게 한다.

보류 이유:

- Search는 발견이 목적이다. 설정이 길어지면 검색 흐름이 무거워진다.
